Overview — what this is & why

Not a conversation browser — a search engine and a dashboard built on top of your CLI history.

This project answers two questions the author keeps asking: "What did I discuss with Claude/Codex about X?" and "Where is my LLM budget actually going?" Everything in the codebase justifies itself against one of two pillars — faster recall (find a past conversation by vague memory) or faster pattern understanding (see cost, tool usage, and session-type breakdowns). Features that don't serve those pillars are explicitly out of scope; see the anti-bloat guardrails in DESIGN.md §7 and docs/CONVERSATIONS_MASTER_PLAN.md §12.

The data pipeline is linear. Raw JSONL transcripts (Claude under ~/.claude/projects/, Codex under ~/.codex/sessions/) are converted to one Markdown file per project by standalone Python scripts. A FastAPI backend parses that Markdown, merges in actual token counts read from the raw JSONL, and upserts everything into Postgres — sessions, segments, tool calls, heuristic topics, session-type classification, a 384-dim semantic embedding per session, and (optionally) a Graphify concept graph. A React 19 single-page app, served by the same FastAPI process, renders three tabs: a resizable three-pane conversation browser, a KPI dashboard, and a d3 force-directed knowledge graph with an in-tab wiki.

It is a single-user, local-first, personal tool. It runs entirely in Docker (one app container + one Postgres container), reads your source JSONL read-only, and never modifies ~/.claude/projects/. The only thing that needs network access is the optional AI-summary and concept-graph features, which shell out to your locally-installed claude CLI from a host-side watcher — no API key required.

The project is feature-complete and feature-frozen at v2.1.1 (shipped 2026-04-22, the end of "Phase 9 — drift remediation & full coverage push"). It went through nine documented migration phases (in-memory index → Postgres → search upgrade → dashboard → semantic search → testing/CI → OOP restructure → wiki integration → drift remediation). Both backend and frontend are held at 100% test coverage in CI. Future work is reactive only: bug fixes and cost-formula tweaks if Anthropic pricing changes.

Key concept
The unit of search is the session (one conversation), not the segment (one request). Embeddings, ranking, and result cards are all session-level. This avoids "chunk spam" where the same conversation dominates results, and makes every hit directly actionable: click through to the conversation. Snippet extraction does a second-pass keyword search within the matched session's segments.
Note on version drift
The authoritative version lives in browser/frontend/package.json, which currently reads 2.2.0. The docs (docs/status.md, docs/versions.md) describe the last documented release as v2.1.1. The numeric package field is the source of truth per the project's own versioning protocol; the doc set just hasn't been re-cut to match the latest bump.

What works today

  • Export — Claude + Codex JSONL → one Markdown file per project (convert_export.py, convert_claude_jsonl_to_md.py, convert_codex_sessions.py).
  • Hybrid search — tsvector keyword + pgvector semantic legs fused via Reciprocal Rank Fusion, with metadata-filter parsing (project:, model:, after:, cost:>, turns:>, …) and a relevance bar per result.
  • KPI dashboard — summary cards, cost-over-time, project/model/tool/session-type breakdowns, activity heatmap, anomaly table, a 4-way cost breakdown, and a Top-5-most-expensive-sessions widget.
  • Knowledge graph — d3 force-directed concept graph from Graphify, with an in-tab wiki pane (community + god-node articles, [[WikiLink]] navigation).
  • Soft delete / restore, dark/light theme, AI summaries (host-side claude watcher), resizable panes.

Architecture

A linear ingest pipeline feeds Postgres; a layered FastAPI backend reads it and serves the React SPA. Two host-side watchers (summaries, graph) call the local claude CLI from outside the container.

End-to-end data flow

Backend layering (routes → services → repositories)

After the Phase 7.1 OOP restructure, the backend is strictly layered. A request enters a thin route handler, which resolves a service via FastAPI dependency injection, which calls one or more repositories, which build SQLAlchemy queries against the models. Filter-to-SQL translation is centralized in one SessionFilterScope dataclass.

Process & container topology

Two containers, two host-side watcher processes. The watchers run outside Docker because they call your locally-authenticated claude CLI — there's no API key in the container.

Key concept — why a separate ingest pipeline and serving path
The Markdown converters (convert_*.py) are deliberately not replaced by direct-JSONL loading. They are the source of truth for conversation structure (the >>>USER_REQUEST<<< delimiter scheme, entry keys, tool-call rendering). jsonl_reader.py only reads back the model name and real token usage that Markdown can't preserve. The two are merged in load.py.

Core modules — the heart of the system

Each drill-down covers what the module does, its key logic, and the exact files. The three load-bearing subsystems are the converters, the data loader (cost + embeddings), and the search/graph services.

Claude converter convert_claude_jsonl_to_md.py

Walks SRC (each subdirectory = one project) and writes one Markdown file per project to DST, ordered chronologically. Invoked as python convert_claude_jsonl_to_md.py <raw/projects> <markdown> by the orchestrator.

Key behaviors:

  • Stable entry keys. Each record gets a deduplication key — a real ID (uuid/id/message_id/…) if present, else a SHA-256 of the record with volatile keys (timestamps, cwd, transcript_path) scrubbed out. Written as an <!-- ENTRY_KEY: … --> comment so re-runs are incremental (load_existing_keys skips already-written entries — but only outside code blocks).
  • The search delimiter. Only messages the user actually typed (is_real_user_message — role "user" and not a tool-result) get the >>>USER_REQUEST<<< marker and an # heading. This is the primary split point the parser keys on.
  • Marker neutralization. neutralize_markers rewrites any >>>USER_REQUEST<<< / ENTRY_KEY / ## Conversation that appears inside quoted content (e.g. a tool result that printed the markdown file itself) so it doesn't create false matches.
  • Internal-tag stripping. Claude internal XML tags (system-reminder, thinking/function-call envelopes, hooks) are removed via regex.
  • Privacy. sanitize_home_paths replaces /Users/<name> and /home/<name> (and their dash-encoded forms) with ~.
  • Tool rendering. render_tool_use emits **Tool Call: `ToolName`** + a fenced JSON block — the exact pattern the parser counts as a tool call.
convert_claude_jsonl_to_md.py~540 lines; the format contract everything downstream parses.
Codex converter convert_codex_sessions.py

Reads Codex session JSONL (one file = one session, event records with payload.type like user_message, agent_message, function_call, function_call_output). Groups sessions by the session's cwd (→ project name) and writes one Markdown file per project. User messages get the same >>>USER_REQUEST<<< marker so the parser treats Codex and Claude output uniformly. reasoning and token_count records are skipped.

convert_codex_sessions.pyCodex → Markdown. Session header is `## Session ...` (vs Claude's `## Conversation ...`).

Markdown parser browser/backend/parser.py

Turns a directory of Markdown files into an in-memory index. The regex contract (lines 32–55) mirrors the converter output exactly. Splitting on USER_REQUEST_DELIM yields one RequestSegment per user request; parts[0] is the preamble. Each segment's conversation_id comes from the heading's conv: suffix or the most recent ## Conversation/Session marker. Tool-call count is just TOOL_CALL_RE.findall. Segment IDs are stable_id(source_file, segment_index) = first 16 chars of SHA256("<file>:<index>").

Token estimate
The parser's estimated_tokens is a rough char_count // 4. This is only used for display in segment metrics — the real cost math in load.py uses actual token counts read from the JSONL message.usage fields.
browser/backend/parser.pybuild_index(), compute_tool_breakdown(), stable_id() — used by load.py and the export pipeline.
JSONL metadata reader browser/backend/jsonl_reader.py

The only place real billing data enters the system. For each Claude JSONL file it sums per-turn usage from every assistant record's message.usage: input_tokens, output_tokens, cache_read_input_tokens, cache_creation_input_tokens, and grabs the first assistant message.model. Subagent files are skipped. Codex only yields model_provider from the session_meta payload (no reliable token usage). Returns a dict[session_id, SessionMetadata] keyed on the JSONL filename stem.

browser/backend/jsonl_reader.pyread_claude_metadata() + read_codex_metadata().
Data loader & cost engine browser/backend/load.py

The merge point. load_all() reads JSONL metadata, parses Markdown via build_index(), groups segments into sessions by conversation_id (standalone segments each become their own session), and upserts everything with Postgres INSERT … ON CONFLICT DO UPDATE for idempotency. Per session it computes a summary (first ~3 user previews), heuristic topics, a session-type classification, and the estimated cost. Tool calls are delete-and-reinsert per session (no natural unique key).

The cost formula is the project's most-scrutinized piece of math. estimate_cost_breakdown is a pure function returning a 4-way CostBreakdown:

Pricing per 1M tokens (MODEL_PRICING): opus-4-6 $15/$75, sonnet-4-6 $3/$15, haiku-4-5 $0.80/$4. Unknown models fall back to sonnet via prefix match then a hard $3/$15 default. Cache-read is billed at 10% of input price; cache-write at 125% (Anthropic's 5-minute-TTL rate — the code deliberately does not detect the 1-hour 2.0× tier or the 1M-context 1.5× tier because the stored JSONL has no per-turn TTL or per-call input-size signal).

Key concept — denormalized cost, recomputed on startup
sessions.estimated_cost is stored denormalized (fast sort key for the Top-5 and anomaly queries). On every app startup, recompute_session_costs() re-scores every row with the current formula and issues an UPDATE only when the stored value drifted by > $0.0001. This means a formula change (like the Phase 7.5 cache-write premium) auto-corrects historical rows with no manual reload. Dashboard display totals come from a fresh group-by-model recomputation, not SUM(estimated_cost), so the headline number and the breakdown stay in sync by construction.

_embed_new_sessions() finds sessions with embedding IS NULL, batch-fetches their topics + tools (3 queries total regardless of session count), builds the compressed session text, embeds, and stores the vector — committing every 100 rows. Wrapped in try/except so a missing model is non-fatal.

browser/backend/load.pyload_all, estimate_cost_breakdown, recompute_session_costs, _embed_new_sessions.
Heuristic enrichment topics.py · classify.py

topics.py scores topic candidates from four signals: project-name segments (confidence 0.8), file extensions mentioned (0.6), keyword matches (0.7), and tool-derived signals (research/shell). It returns up to 5 (topic, confidence) tuples. Graphify concepts, when present, are merged into session_topics later with source='graphify' and 0.9 confidence (higher than any heuristic tag).

classify.py assigns one of coding / debugging / planning / research / writing / devops by ordered rules: devops topic keywords first, then Edit+Write>3 → coding, Bash>5 + "error" → debugging, low-tool + many-words → planning, web search → research, short no-edit → research, else coding.

browser/backend/topics.pyextract_topics().
browser/backend/classify.pyclassify_session().
Embedding pipeline browser/backend/embed.py

Lazy-loads sentence-transformers/all-MiniLM-L6-v2 via huggingface_hub on first call (downloads tokenizer.json + onnx/model.onnx). embed_text(text) tokenizes (max 256 tokens, padded), runs ONNX inference, mean-pools token embeddings masked by attention, L2-normalizes, and returns a 384-dim Python list. build_session_text() assembles the compressed representation that gets embedded:

browser/backend/embed.pyembed_text(), build_session_text(), _ensure_model().
Concept-graph extraction graph_extract.py

Runs on the host (via the launcher's graph watcher), not in the container, because it shells out to claude -p. For each Markdown file: if a chunk cache exists, skip; small files (<512KB) are sent raw, larger ones are condensed (condense_markdown strips assistant responses, tool output, code blocks — keeping only conversation headers and the first ~300 chars of each user request, a 95–99% reduction). The condensed body is capped at 120K chars and piped to claude -p --model … --system-prompt ….

Key concept — system prompt separation
The extraction instructions go through --system-prompt, architecturally separate from the document content piped on stdin. This stops Claude from treating the conversation log as a conversation to continue — it forces pure JSON extraction. The system prompt also pins file_type to the 5-value Graphify enum.

Per-file results cache to .graphify_chunk_*.json. build_graph() merges all chunks (deduping node IDs, normalizing file_type via FILE_TYPE_ALIASES), then calls graphifyy's build_from_json → cluster → to_json and to_wiki. The wiki gets community articles + the top-15 god-node (highest-degree) articles. Progress and status are written to .progress / .status files the frontend polls.

graph_extract.pycondense_markdown, extract_file, build_graph, _derive_god_nodes, _normalize_file_type.
browser/backend/import_graph.pyReads graph.json, maps nodes to sessions by source-file stem, populates concepts + session_concepts, merges into session_topics.
SearchService — hybrid retrieval browser/backend/services/search_service.py

The recall engine. search() parses the query (parse_query peels off structured filters), builds a SessionFilterScope, and routes to hybrid retrieval (when free text remains) or filter-only retrieval. Hybrid:

  1. Keyword leg — tsvector top-50 sessions via SegmentRepository.search_keyword_top_sessions.
  2. Vector leg — embed the query, cosine-distance top-50 via SessionRepository.search_vector_top_sessions (lazy import of embed; any failure falls back to keyword-only).
  3. RRF fusion — _rrf_merge with k=60, normalized to [0,1].
  4. Final scoring — 0.6·rrf + 0.2·recency + 0.1·length + 0.1·exact_match.
  5. Community boost — +0.05 × shared-Leiden-community-count with the top result (returns {} when no concept data).
  6. Snippets — second-pass keyword search inside each matched session's segments; falls back to summary text.

get_status() drives the UI mode badges (unavailable / keyword / embedding / hybrid) from visible-vs-embedded session counts plus concept-community presence.

services/search_service.pySearchService + module-level scoring helpers.
services/_filter_scope.pySessionFilterScope — compiles SearchFilters into WHERE clauses + tool/topic subqueries once per request.
search.pyparse_query() + SearchFilters/ParsedQuery models. Malformed filters fall back into free text.
DashboardService — aggregations browser/backend/services/dashboard_service.py

A read-model service — pure SQL aggregations, no writes. Queries the session directly (its 9 view shapes would bloat per-model repos). All endpoints share a DashboardFilters bag (provider, date_from/to, project, model) applied via .apply(stmt). Cost numbers are always computed by grouping on model and pricing each group through estimate_cost_breakdown then summing — never SUM(estimated_cost) — so the headline total equals the sum of the 4-way breakdown.

Highlights: get_top_expensive_sessions orders by stored estimated_cost DESC (index-backed) but recomputes each row's breakdown for display, surfacing cache_read_pct — the single most important transparency signal (sessions whose bill is dominated by cached-context re-reads). get_graph auto-imports graph.json on first request and caps the graph at the 200 highest-degree concepts to keep d3 responsive.

services/dashboard_service.pyget_summary, cost-over-time, projects/tools/models, session-types, heatmap, anomalies, top-expensive, get_graph.
GraphService — the wiki surface browser/backend/services/graph_service.py

Owns the file-protocol the host watcher uses (trigger / status / progress files) plus the Phase 8 wiki endpoints. resolve_wiki_slug precedence: a god-node article by display name wins over a community article (looked up via concepts.community_id). _wiki_slug reimplements graphifyy's filename rule (three literal substitutions, locked by a parity test).

Watch out — path traversal guard
_safe_wiki_path resolves wiki/{slug}.md and asserts it stays under the wiki root via Path.relative_to(); any escape returns None → the route returns 404. Note: httpx's ASGITransport URL-decodes %2F before routing, so a wire-level ../ test hits the SPA catch-all instead — the definitive coverage is the service-level test_safe_wiki_path_rejects_traversal_with_parent.
services/graph_service.pyload_wiki_index, load_wiki_article, resolve_wiki_slug, _safe_wiki_path, trigger_regeneration, import_from_disk.
SummaryService — host-side AI summaries browser/backend/services/summary_service.py

A filesystem state machine. The service writes <id>.input + <id>.pending markers into SUMMARIES_DIR; the host watcher polls for *.pending, runs claude -p, writes <id>.md (first line TITLE: …), and deletes the markers. The service reads the result back and exposes none/pending/ready states. Conversation summaries use a hierarchical rollup (chunk into ~80K-char pieces, cascade). Cached summaries survive container restarts because the directory is a bind mount.

services/summary_service.pyrequest/get/delete segment + conversation summaries; the .pending/.input/.md protocol.
summary_watcher.shThe host-side poller (logic also inlined in export_service.sh::start_summary_watcher).

One repository per model. They own all SQLAlchemy query construction and accept a SessionFilterScope to stay ignorant of SearchFilters' structure. How to run it

One command starts everything. The launcher exports conversations, builds + starts the Docker stack, spawns the watchers, and drops into a k/q/v/r shutdown loop.

Full run (Docker)

  1. Have Docker Desktop running and Python 3.10+ on PATH (for the export step only).
  2. macOS/Linux: run export_service.sh. Windows: run export_service.bat.
  3. The script exports ~/.claude/projects/ → ./markdown/, runs docker compose up --build -d, syncs Postgres, starts the summary + graph watchers.
  4. Open http://localhost:5050 (auto-opened on success).

Startup flags: --skip-export (use existing markdown), --export-only (no browser), or a bare project-name to filter the export. Override the port with PORT=8080 ./export_service.sh.

Shutdown / restart loop

KeyContainersImagesVolumesGenerated dataRestarts?
kStoppedKeptKeptKeptNo
qRemovedRemovedKeptKeptNo
vRemovedRemovedRemovedDeletedNo
rRemovedRemovedRemovedDeletedYes — re-exports, rebuilds, relaunches

Any unrecognized key reprints the menu. v and r wipe raw/ markdown/ markdown_codex/ browser_state/ graphify-out/ but never touch ~/.claude/projects/.

Local dev (no Docker, hot reload)

  1. Backend: cd browser/backend && pip install -r requirements.txt && MARKDOWN_DIR=../../markdown uvicorn app:app --reload --port 5050 (needs a running Postgres reachable via DATABASE_URL).
  2. Frontend: cd browser/frontend && npm install && npm run dev — Vite serves on :5174 and proxies /api to :5050.
Watch out — Windows .bat in a non-TTY runner
The interactive k/q/v/r prompt uses set /p, which hangs in a non-interactive batch run (e.g. PyCharm's right-click "Run"). Launch the .bat from a real terminal (or enable "Emulate terminal in output console").

How to edit & extend it

Practical, owner-focused. "To add X, touch these files." The backend's strict layering means most additions follow the same route → service → repository path.

Add a new API endpoint
  1. Define the response shape in schemas.py (a Pydantic model).
  2. Add the query/aggregation method to the relevant service in services/ (or a repository if it's a single-model query).
  3. Add a thin handler to the matching router in routes/ — parse params, Depends(get_*_service), call the method, return it. Declare response_model=.
  4. If it's a new resource, register the router in app.py.
  5. Add a fetch wrapper in api.js, then wire it into a component/hook.
  6. Add tests under tests/ (services + repositories are directly traced; route tests assert real DB state). CI gates at 100% coverage — untested lines fail the build.
Add or change a database column

Edit the model in models.py and the matching Pydantic schema. There is no migration system — apply the change by wiping the volume and reloading: docker compose down -v then re-run the launcher (or load.py). For a sacred-contract table, update the master plan first (see §7 of this doc).

Change the cost formula or add a model price

Edit MODEL_PRICING (add a "model-name": (input, output) entry) and/or the premium constants in load.py. Because recompute_session_costs() runs on every startup, the change auto-applies to historical rows — no manual reload needed. Add a canonical case to tests/test_load_cost.py. Document the rationale in master plan §5.

Add a new search filter prefix
  1. Add a field to SearchFilters and a pattern to _FILTER_PATTERNS in search.py.
  2. Translate it to a WHERE clause in _filter_scope.py (SessionFilterScope.build).
  3. If it should appear as an autocomplete chip, surface its distinct values in SearchService.get_filters and render the chip in FilterChips.jsx.
Add a dashboard chart
  1. Add the aggregation to dashboard_service.py and an endpoint to routes/dashboard.py (respect DashboardFilters so it coordinates with global filters).
  2. Add a fetcher to api.js.
  3. Build the chart component (Chart.js via react-chartjs-2 — see Charts.jsx) and mount it in Dashboard.jsx.
Do not
Don't add features that assume manual browsing of old conversations, per-turn cost attribution, manual tagging, or tool-output indexing. The anti-bloat guardrails in DESIGN.md §7 reject these explicitly.
Change the Markdown format / parser

The converter (convert_claude_jsonl_to_md.py) and the parser (parser.py) share an implicit contract: the >>>USER_REQUEST<<< delimiter, the # User #N — <ts> — conv: heading, the <!-- ENTRY_KEY: … --> comment, and **Tool Call: `Name`**. If you change one, change the other, and update the regexes in parser.py lines 32–55.

Decompose / add a frontend component or hook

One concept per file. Components live in components/, hooks (named useX.js) in hooks/, each with a test in __tests__/. The flat 100/100/100 vitest gate means every branch needs a test — extract pure helpers (the pattern Phase 9 used for Dashboard.jsx and ConceptGraph.jsx) when d3/Chart.js callbacks aren't reachable in jsdom.

Build, CI & deployment

GitHub Actions (this project is open-source on GitHub — a documented override of the author's GitLab default). Two workflows.

ci.yml — six jobs

Notable: test-backend pre-pulls the pgvector image to warm the testcontainer cache, installs libgomp1, and sets TESTCONTAINERS_HOST_OVERRIDE=localhost (the conftest assumes macOS Docker Desktop's host.docker.internal, wrong on Linux runners). docker-build verifies the multi-stage image with GHA layer cache but does not push.

release.yml — manual semver bump

A workflow_dispatch-only workflow (gated to main) bumps the version field in browser/frontend/package.json — the project's source of truth (the backend pyproject.toml has no [project] block) — then tags and pushes. Never edit the version field directly.

Docker image

Multi-stage (Dockerfile): node:20-alpine runs npm ci + npm run build; python:3.13-slim installs runtime deps + libgomp1, copies the backend, the converter scripts, and the built dist/ into /app/static, then runs uvicorn. A .dockerignore trims the build context.

Domain glossary

Terms a newcomer needs to read the code.

Session
One conversation. The atomic unit of search, embedding, ranking, and cost. Keyed by conversation_id (or, for standalone segments, the segment's own id).
Segment
One user request + its following assistant/tool content, split on the >>>USER_REQUEST<<< delimiter.
Provider
claude or codex — the CLI the transcript came from.
RRF (Reciprocal Rank Fusion)
Merges the keyword and vector ranked lists by rank position (1/(k+rank), k=60) without normalizing incompatible score scales.
tsvector
Postgres full-text search type. search_vector columns are generated from text; GIN-indexed for keyword ranking via ts_rank.
pgvector / HNSW
The Postgres vector extension + the approximate-nearest-neighbor index used for cosine-similarity search over session embeddings.
Graphify (graphifyy)
The optional sidecar that turns Markdown into a concept graph with Leiden community detection and a generated wiki.
God node
A highest-degree concept in the graph. The top-15 get their own wiki article.
Community
A Leiden cluster of related concepts. Drives node coloring, wiki community articles, and the optional search re-ranking boost.
cache_read / cache_creation tokens
Anthropic prompt-caching token buckets. Cache-read is billed at 10% of input price; cache-creation at 125% (5-minute TTL) in this project's formula.
Cost breakdown
The 4-way split — input / output / cache-read / cache-write USD — that the dashboard and per-session views render.
Watcher
A host-side background process the launcher spawns to call the local claude CLI (one for summaries, one for graph extraction).
